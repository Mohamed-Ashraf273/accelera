\begin{abstract}
\project{} is a hybrid Python/C++ machine learning framework designed to combine
Python's modelling productivity with C++ execution infrastructure. The project
contains graph-based machine learning pipelines, parallel branch execution,
HTML reporting, AutoML preprocessing utilities, dataset retrieval, deployment
support, benchmarking infrastructure, and a Linux-only C/C++ loop
parallelizer. This report is organized around five project modules:
\texttt{accelera\_pipe}, the code parallelizer, AutoML, deployment, and the
benchmark platform. The \texttt{accelera\_pipe} module constructs and executes
directed machine learning workflows using a Python API over a C++ graph
backend. The code parallelizer analyzes source loops, extracts features,
classifies loops, and injects OpenMP pragmas. The remaining module sections are
reserved for future expansion.
\end{abstract}

\section{Project Introduction}

\project{} targets experimental and production-oriented machine learning
workflows where a user wants to express a pipeline in Python while delegating
graph execution and branch scheduling to a compiled backend. Its main design
idea is to represent preprocessing, model training, prediction, merging, and
metric computation as graph nodes. Independent branches can then be evaluated
in parallel, making it convenient to compare alternative preprocessors,
estimators, and metrics in a single run.

The repository also includes a code parallelizer that operates outside the ML
pipeline. That subsystem parses C/C++ source code through Clang AST bindings,
extracts loop fragments, computes structural and dependency-related features,
consults a remote classifier service, and inserts OpenMP \texttt{parallel for}
pragmas where the loop appears safe or useful to parallelize. If the input file
is Python, a small AST-based converter first emits equivalent C++ for a limited
subset of Python syntax before loop analysis begins.

\section{Accelera Pipe Module}

\subsection{Module Location and Responsibility}

The \texttt{accelera\_pipe} module is implemented under
\modulepath{accelera/src/accelera\_pipe/}. It provides the Python API for
building graph pipelines and report objects. Its core files are:

\begin{itemize}[leftmargin=*]
  \item \modulepath{core/pipeline\_base.py}: wraps the C++ \texttt{graph.Graph}
        object and exposes shared configuration methods.
  \item \modulepath{core/pipeline.py}: public builder API for preprocessing,
        model, prediction, metric, merge, and branch nodes.
  \item \modulepath{core/executed\_graph.py}: reusable executed graph wrapper.
  \item \modulepath{core/metric.py}: abstract metric interface.
  \item \modulepath{wrappers/supervised\_metric.py} and
        \modulepath{wrappers/unsupervised\_metric.py}: concrete metric
        adapters.
  \item \modulepath{core/report\_base.py} and wrapper display classes:
        HTML report generation for pipeline graphs and metrics.
\end{itemize}

\subsection{Graph Backend}

\texttt{PipelineBase} imports the native \texttt{graph} module. If this module
is missing, it raises an import error that instructs the user to build the C++
bindings and make them available in \texttt{PYTHONPATH}. When initialized, the
base class creates or reuses a \texttt{graph.Graph} instance and enables
parallel execution by default:

\begin{lstlisting}[language=Python]
self.__graph = _graph if _graph is not None else graph.Graph()
self.__graph.enableParallelExecution(True)
\end{lstlisting}

The node type mapping bridges Python method names to C++ enum values:
\texttt{PREPROCESS}, \texttt{MODEL}, \texttt{PREDICT}, \texttt{METRIC}, and
\texttt{MERGE}.

\subsection{Pipeline Builder API}

\texttt{Pipeline} is the main user-facing class. Each method either appends a
node to the graph or, when \texttt{branch=True}, returns a lightweight
\texttt{Node} object that can be supplied to \texttt{branch()}.

\subsection{Execution Semantics}

Calling a \texttt{Pipeline} executes the underlying graph:

\begin{lstlisting}[language=Python]
predictions, executed_graph = pipe(X, y, select_strategy="all")
\end{lstlisting}

The C++ backend returns an executed graph plus result values. The Python layer
wraps the first returned item in \texttt{ExecutedGraph}; all remaining returned
items are predictions or metric outputs. The selection strategy can be
\texttt{all}, \texttt{max}, \texttt{min}, or a user-provided
\texttt{custom\_strategy}. Tests in the module show that these strategies are
used to select paths according to metric outputs.

\subsection{Preprocessing and Model Fitting}

Preprocess nodes store the transformation object or function together with
\texttt{execute\_fit}, a helper that determines whether a component should be
fit with \texttt{X} only or with both \texttt{X} and \texttt{y}. This lets the
pipeline handle unsupervised transformers such as scalers and supervised
transformers such as feature selectors. Model nodes similarly store the model
object and fitting helper, allowing sklearn-compatible estimators and custom
Accelera estimators to participate in the graph.

\subsection{Prediction Nodes}

\texttt{predict(name, test\_data, output\_func="predict", positive\_class=-1)}
records the data on which the trained model should be evaluated. The
\texttt{output\_func} parameter can request outputs such as \texttt{predict} or
\texttt{predict\_proba}. When probabilities are used, \texttt{positive\_class}
can select one probability column.

\subsection{Metric Nodes}

The pipeline maps metric names to functions from \texttt{sklearn.metrics}.
Then the metric-class helper inspects the metric function signature:

\begin{itemize}[leftmargin=*]
  \item A metric with true labels and predicted labels/scores becomes a
        \texttt{SupervisedMetric}.
  \item A metric with \texttt{X} and \texttt{labels} becomes an
        \texttt{UnSupervisedMetric}.
  \item Any incompatible signature is rejected.
\end{itemize}

\texttt{SupervisedMetric.execute} validates that \texttt{y\_pred} and
\texttt{y\_true} have the same number of samples, then calls the sklearn metric.
\texttt{UnSupervisedMetric.execute} validates predictions against the stored
input \texttt{X}. Both return a dictionary containing the metric name, result,
plot function, label names, and header names.

\subsection{Branching and Merging}

\texttt{branch()} accepts one or more branch node objects. Each branch can be a
single node or an iterable of nodes. The method validates that all branch
members are \texttt{Node} instances and rejects merge nodes inside branches
because merge-in-branch behavior is not implemented yet. The validated branch
objects, node types, and node names are passed to the C++ graph through
\texttt{split()}.

Merge nodes combine multiple branch outputs. The default strategy is
\texttt{hard\_voting}. The test suite covers hard-voting merges, merges after
preprocessing branches, probability prediction merges, single-model merges, and
reuse of executed graphs after merging.

\subsection{Executed Graphs}

\texttt{ExecutedGraph} wraps a graph that has already been fitted or selected.
Calling it with new \texttt{X} reuses the fitted pipeline. If \texttt{y\_true}
is provided, metrics are temporarily enabled for that call and disabled
afterward.

Executed graphs can now be persisted as a single pickle file. Calling
\texttt{save()} with no arguments creates \texttt{pipeline.pkl} in the current
working directory. The user may also pass an explicit file path such as
\texttt{"my\_pipeline.pkl"}. Loading is performed through
\texttt{ExecutedGraph.load()}, which reconstructs the native C++ graph and
restores the fitted Python objects stored in the graph nodes. The loaded graph
keeps the executed-state flag, so applying data to it performs inference
directly rather than fitting the models again.

\begin{lstlisting}[language=Python]
predictions, executed_graph = pipeline(X_train, y_train)

executed_graph.save()                  # writes pipeline.pkl
loaded_graph = ExecutedGraph.load()    # reads pipeline.pkl

test_predictions = loaded_graph(X_test)
\end{lstlisting}

The implementation uses a pybind pickle bridge for the C++ \texttt{Graph}
object. During saving, the graph is converted into a Python dictionary
containing node metadata, source-edge indices, selected-path flags, fitted
preprocessors, and fitted model state. During loading, this dictionary is used
to rebuild the graph topology and restore each node. This design stores the
pipeline in one file, but it requires the Python objects inside the pipeline to
be pickle-compatible; standard sklearn transformers and estimators satisfy
this requirement, while lambdas and some local custom functions may not.

\subsection{Reporting}

The reporting layer creates HTML reports rather than PDF reports. The base
class \texttt{ReportBase} defines the HTML shell and utility functions.
\texttt{GraphReport} reads serialized pipeline XML, builds a Graphviz diagram,
colors selected path nodes red and other nodes blue, lists branches, and then
delegates metric rendering to \texttt{GraphPipelineReport}.

The graph-pipeline report groups metric records by metric name and chooses a
display wrapper according to the result type:

\begin{itemize}[leftmargin=*]
  \item scalar values: \texttt{DisplaySingleNumber};
  \item one-dimensional arrays: \texttt{DisplayArraySingle};
  \item multi-dimensional arrays: \texttt{DisplayMultiArray} or
        \texttt{DisplayFigure};
  \item dictionaries: \texttt{DisplayDict};
  \item strings: \texttt{DisplayString};
  \item tuples: \texttt{DisplayTupleNotCurve} or \texttt{DisplayFigure}.
\end{itemize}

\texttt{ModelReport} reuses this metric rendering and can optionally plot
training history when a dictionary of history arrays is provided.

\subsection{Empirical Comparison with sklearn}

To evaluate the execution behavior of \texttt{accelera\_pipe}, a controlled
comparison was performed against two sklearn baselines. The first baseline
uses a direct manual sklearn loop, where each candidate scaler and model is
cloned, fitted, evaluated on validation data, and then the selected candidate
is evaluated on test data. The second baseline uses \texttt{sklearn.pipeline}
with the same candidate pairs. The \project{} version expresses the same
candidate space as two graph branches: two preprocessing alternatives
(\texttt{StandardScaler} and \texttt{MinMaxScaler}) followed by two model
alternatives (\texttt{LogisticRegression} and \texttt{SVC}). Therefore, all
systems evaluate four candidate pipelines and select the path with the highest
validation accuracy.

The experiment uses synthetic four-class classification data with 25 features.
Each dataset is split into 60\% training, 20\% validation, and 20\% test data.
The validation split is used only for candidate selection, while the test
split is used to report final accuracy. Table~\ref{tab:pipe-sklearn-benchmark}
shows that all three implementations selected an equivalent best candidate and
obtained the same test accuracy in every run. For small inputs, the native
graph overhead dominates; for larger inputs, the parallel branch execution of
\texttt{accelera\_pipe} reduces latency compared with both sklearn baselines.
The memory measurements also show that \texttt{accelera\_pipe} currently pays
a larger memory cost because multiple graph branches and fitted node states
can be alive at the same time.

\subsection{Implemented Pipeline Optimizations}

Several optimizations were added to reduce unnecessary work and memory
retention in the native graph backend. These changes target the main cost of
branch-based pipeline search: multiple candidate paths can hold similar
intermediate arrays, fitted states, and prediction outputs at the same time.

\paragraph{Optional cache execution.}
Caching for preprocess and model nodes was made opt-in. The public Python API
keeps the parameter \texttt{cache=False} by default for both
\texttt{preprocess()} and \texttt{model()}. When caching is disabled, the C++
nodes skip the expensive \texttt{joblib.hash()}, \texttt{joblib.load()}, and
\texttt{joblib.dump()} path. This reduces latency and memory pressure in normal
search runs, while preserving cache support for repeated experiments where the
user explicitly enables it.

\paragraph{Consumer-count based intermediate release.}
The graph backend now computes how many downstream nodes still consume each
node output. After a node finishes, the consumer count of its source nodes is
decremented. When the count reaches zero, temporary data for releasable nodes
is cleared. This is especially important for preprocessing outputs, because a
transformed training array may be needed by multiple model branches but becomes
dead once the last model has finished fitting.

\paragraph{Input training-data release.}
The original input node stores the raw training \texttt{X} and \texttt{y}.
After all downstream training consumers have executed, these references are
cleared as well. This prevents the graph from retaining the original training
arrays after fitted preprocessors and models no longer require them. The
release is disabled for executed graphs during inference, because the executed
graph input must remain available while prediction nodes apply the fitted
preprocessing chain to new test data.

\paragraph{Separated output-container creation from input copying.}
Originally, the internal flag \texttt{should\_create\_new\_data} controlled two
different behaviors: creating a fresh branch output container and copying
\texttt{X}/\texttt{y} before preprocessing. These meanings were separated into
two concepts. A first preprocessing node in a branch still creates its own
output dictionary, but the decision to defensively copy the input is controlled
independently. This avoids corrupting branch storage semantics while allowing
safe copy reduction.

\paragraph{Guarded defensive-copy reduction for preprocessing nodes.}
The graph separates branch-output creation from input-copy decisions through
the \texttt{shouldCopyPreprocessInput()} helper. A return value of
\texttt{true} means that the preprocessing node receives defensive copies of
\texttt{X} and \texttt{y}; a return value of \texttt{false} means that the node
can safely read the existing branch input without copying it first. The helper
first rejects non-preprocessing nodes, then inspects the Python preprocessing
object stored under the \texttt{func} key. Non-sklearn callables remain
conservative and are copied, because an arbitrary user function may mutate its
input in place.

For sklearn transformer instances, copying is disabled only when the
transformer is not configured for in-place mutation. The implementation calls
\texttt{get\_params(deep=False)} when available and checks the sklearn
\texttt{copy} parameter. If \texttt{copy=False}, the graph keeps the defensive
copy because the transformer is explicitly allowed to mutate its input. If the
parameter is absent or inspection succeeds without finding an unsafe
configuration, the copy is skipped. If inspection raises a Python error, the
backend clears the error and falls back to copying. This design reduces memory
for common sklearn preprocessors such as \texttt{StandardScaler} and
\texttt{MinMaxScaler} under their default settings, while preserving isolation
for custom callables and sklearn transformers configured with
\texttt{copy=False}.

\paragraph{Executed-graph data retention reduction.}
Executed graph cloning keeps the fitted model state needed for future
prediction, but avoids carrying unnecessary training intermediates such as raw
training arrays and preprocessing output dictionaries. The selected executable
path therefore keeps fitted preprocessors and fitted models as reusable state,
while temporary training data can be released.

\paragraph{Duplicate first-branch-node sharing.}
The split operation now deduplicates identical first nodes created from the
same split source. For example, if a branch is declared as:

\begin{lstlisting}[language=Python]
pipe.branch(
    "preprocessing",
    pipe.preprocess("a", MinMaxScaler(), branch=True),
    pipe.preprocess("b", StandardScaler(), branch=True),
    pipe.preprocess("c", MinMaxScaler(), branch=True),
)
\end{lstlisting}

the graph creates one \texttt{MinMaxScaler} node and one
\texttt{StandardScaler} node rather than two equivalent
\texttt{MinMaxScaler} nodes. The signature used for this sharing depends on
the node type and Python object representation, not on the user-facing node
name, so identical operations with different names can still be shared.

The optimization is intentionally restricted to first branch nodes. For list
branches, only the first item is eligible for sharing:

Later nodes are not merged, even if they have the same operation name or object
representation, because their inputs may differ. For example,
\texttt{[p1, p2, p3]} and \texttt{[p4, p2, p3]} keep separate \texttt{p2}
nodes because one \texttt{p2} receives data from \texttt{p1}, while the other
receives data from \texttt{p4}. This preserves correctness while removing
obvious duplicate work at branch entry points.

\paragraph{Fair benchmark protocol.}
The comparison script was adjusted so manual sklearn, sklearn Pipeline, and
\texttt{accelera\_pipe} follow the same protocol: train and validate all four
candidate paths, select the best validation path, and evaluate the test split
only once for the selected path. This makes latency comparisons more
meaningful by avoiding extra test predictions in the sklearn baselines.

\subsection{How to Use the Accelera Pipe Module}

A minimal classification pipeline is:

\begin{lstlisting}[language=Python]
from sklearn.datasets import make_classification
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler

from accelera.src.accelera_pipe.core.pipeline import Pipeline

X, y = make_classification(n_samples=1000, n_features=20, random_state=42)
X_test, y_test = X[:100], y[:100]

pipe = Pipeline()
pipe.preprocess("scale", StandardScaler())
pipe.model("logreg", LogisticRegression(max_iter=1000))
pipe.predict("predict", test_data=X_test)
pipe.metric("accuracy", "accuracy_score", y_true=y_test)

results, executed_graph = pipe(X, y)
print(results)
\end{lstlisting}

A branching experiment compares preprocessors and models:

\begin{lstlisting}[language=Python]
from sklearn.ensemble import RandomForestClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import MinMaxScaler, StandardScaler

pipe = Pipeline()
pipe.branch(
    "preprocessing",
    pipe.preprocess("standard", StandardScaler(), branch=True),
    pipe.preprocess("minmax", MinMaxScaler(), branch=True),
)
pipe.branch(
    "models",
    pipe.model("logreg", LogisticRegression(max_iter=1000), branch=True),
    pipe.model("forest", RandomForestClassifier(n_estimators=50), branch=True),
)
pipe.predict("predict", test_data=X_test)
pipe.metric("accuracy", "accuracy_score", y_true=y_test)

results, executed_graph = pipe(X, y, select_strategy="max")
best_result = executed_graph(X_test, y_test)
\end{lstlisting}

To generate a graph report:

\begin{lstlisting}[language=Python]
from accelera.src.accelera_pipe.wrappers.graph_report import GraphReport
from accelera.src.utils.accelera_utils import serialize

results, executed_graph = pipe(X, y, select_strategy="max")
serialize(pipe, "pipeline.xml")

report = GraphReport("pipeline_report", "pipeline.xml", results)
report.execute()
\end{lstlisting}

\section{Code Parallelizer Module}

\subsection{Module Location and Responsibility}

The parallelizer is implemented mainly in
\modulepath{accelera/src/utils/parallelizer.py}. Its Python-to-C++ helper is in
\modulepath{accelera/src/utils/py2cpp\_converter.py}. Native loop extraction is
provided by the pybind module \modulepath{code\_parallelizer\_utils}, which is
built from C++ sources under \modulepath{src/ast/} and
\modulepath{src/utils/code\_parallelizer\_utils.cpp}. The CMake configuration
enables these bindings only on Linux with LLVM/Clang available.

Conceptually, the module implements the following pipeline:

\begin{enumerate}[leftmargin=*]
  \item Read a C, C++, or supported Python file.
  \item Convert Python input to C++ when the file extension is \texttt{.py}.
  \item Extract loops using Clang-backed native bindings.
  \item Cache extracted loop metadata in \modulepath{.accelera\_cache}.
  \item Compute a 40-dimensional feature vector for each \texttt{for} loop.
  \item Send the vector to the classifier endpoint configured by
        \texttt{ACCELERA\_CLASSIFIER\_ENDPOINT}.
  \item Resolve the final loop class with local heuristics.
  \item Generate OpenMP pragmas and replace the original loop text.
  \item Write \texttt{parallelized\_<name>.c} beside the input file and format
        it with \texttt{clang-format} when available.
\end{enumerate}

\subsection{Native Loop Extraction}

The public loop extraction helpers wrap the native
\texttt{code\_parallelizer\_utils} bindings. The default Clang argument is
\texttt{-std=c++17}. The expected extracted loop records include at least the
loop source code, loop type, start line, and end line. Although the C++ AST
layer can identify several loop kinds, the Python insertion logic currently
parallelizes only loops whose extracted \texttt{type} is \texttt{for}.

\subsection{Feature Extraction}

The function \texttt{extract\_features(code)} performs lightweight static
analysis using regular expressions after comment removal. The extracted
features are intentionally pragmatic: they describe loop structure, reduction
patterns, memory access shape, control flow, and rough computational intensity.
Important feature groups include:

\begin{itemize}[leftmargin=*]
  \item \textbf{Reduction features}: detection of scalar \texttt{+=},
        \texttt{x = x + ...}, \texttt{*=}, \texttt{x = x * ...}, and textual
        \texttt{min}/\texttt{max} usage.
  \item \textbf{Dependency features}: loop-carried dependency patterns such as
        \texttt{a[i - 1]}, read-after-write flags, write-after-read flags, and
        dependency distance.
  \item \textbf{Memory features}: array reads, array writes, indirect indexing,
        number of memory operations, and hashed array-name embeddings.
  \item \textbf{Control-flow features}: branch count, early exits via
        \texttt{break}, \texttt{continue}, or \texttt{return}, and function call
        counts.
  \item \textbf{Shape features}: constant loop bounds, estimated iteration
        count, consecutive nested loop depth, and nested brace depth.
  \item \textbf{Vectorization hint}: a boolean flag that becomes true when the
        loop has no branches, no function calls, no loop-carried dependency,
        and no indirect access.
\end{itemize}

\subsection{Vectorization for the Classifier}

\texttt{vectorize\_features(features)} maps the feature dictionary to a
40-element \texttt{numpy.float32} vector. Boolean features occupy positions
0--16. Counts and normalized scalar descriptors occupy later positions. Array
names are transformed into compact deterministic hash vectors rather than sent
as raw strings. This representation is sent as JSON to the remote classifier:

\begin{lstlisting}[language=Python]
response = requests.post(
    classifier_endpoint,
    json={"embedding": features.tolist()},
    timeout=config.REQUEST_TIMEOUT_S,
)
\end{lstlisting}

The classifier result is expected to contain \texttt{result}, which is then
interpreted as a predicted loop class.

\subsection{Loop Class Resolution}

The function \texttt{\_resolve\_loop\_class(loop\_code, pred\_class)} combines
remote prediction with local safety heuristics. If the classifier predicts a
class other than \texttt{none}, that class is used. If it predicts
\texttt{none}, the local logic can still upgrade the loop to:

\begin{itemize}[leftmargin=*]
  \item \texttt{reduction}, when scalar reduction updates are detected.
  \item \texttt{parallel\_for}, when consecutive nested \texttt{for} loops are
        detected.
\end{itemize}

Otherwise the loop remains \texttt{none}. This means the module is not purely
ML-based; it is a hybrid predictor with deterministic fallbacks for common
OpenMP-friendly patterns.

\subsection{OpenMP Pragma Generation}

\texttt{\_generate\_omp\_pragma\_with\_loop} creates the final annotation. For
ordinary parallel loops it emits:

\begin{lstlisting}[language=C]
#pragma omp parallel for
for (...) {
    ...
}
\end{lstlisting}

For consecutive nested loops it adds \texttt{collapse(depth)}. For scalar
addition or multiplication reductions it adds \texttt{reduction(+ : var)} or
\texttt{reduction(* : var)}. The generator therefore currently focuses on
OpenMP \texttt{parallel for}, \texttt{collapse}, and scalar reduction clauses.

\subsection{Generator Model Trial and Rule-Based Design Rationale}

An earlier generator trial attempted to learn OpenMP pragma generation as a
sequence-to-sequence problem. In that formulation, the input sequence contained
the loop source code prefixed by a class token such as
\texttt{[CLS:parallel\_for]} or \texttt{[CLS:reduction]}, and the target
sequence was the expected OpenMP pragma. The implemented model was a custom
PyTorch encoder-decoder network:

\begin{itemize}[leftmargin=*]
  \item \textbf{Encoder}: a bidirectional LSTM with embeddings, dropout, packed
        variable-length input handling, and layer normalization.
  \item \textbf{Decoder}: an LSTM decoder conditioned on Bahdanau additive
        attention over encoder states.
  \item \textbf{Bridge}: linear projections that map the bidirectional encoder
        hidden and cell states into the decoder state space.
  \item \textbf{Training}: teacher forcing, cross-entropy loss with padding
        ignored, Adam optimization, gradient clipping, and a
        ReduceLROnPlateau scheduler.
\end{itemize}

The deployed generator service in \modulepath{models/open\_mp\_generator/app.py}
uses the following configuration: embedding size 128, hidden size 256, three
LSTM layers, dropout 0.2, greedy decoding, maximum input length 1500, and a
checkpoint saved as \modulepath{best\_model.pth}. The tokenizer is a custom BPE
tokenizer rather than a pretrained Hugging Face tokenizer. It is stored in
\modulepath{tokenizer.json}, uses the special tokens \texttt{<PAD>},
\texttt{<UNK>}, \texttt{<SOS>}, and \texttt{<EOS>}, and was configured for a
target vocabulary of 8000 tokens. The saved tokenizer contains 8002 tokens and
7888 learned BPE merges.

Although this neural generator is expressive, two empirical limitations made a
pure learned generator unsuitable for the current system. First, the available
training data was small for a code-generation task and contained only a limited
effective number of examples for some pragma classes. In particular, the corpus
included about 15k negative examples and a comparatively narrow distribution of
positive pragma patterns, which made the sequence model prone to memorization
and overfitting. As a result, validation performance did not reliably imply
generalization to unseen loop structures, variable names, dependency patterns,
or clause combinations.

Second, expanding the corpus with AI-generated examples introduced distribution
bias. Synthetic loops and pragmas tend to reflect the style, templates, and
regularities of the generating tool. A model trained heavily on such data can
learn those artifacts instead of learning robust OpenMP semantics. This lowers
real-world generalization even when apparent training or validation error looks
acceptable on similarly generated samples.

For these reasons, the implemented generator path was changed to a rule-based
approach. OpenMP pragmas are now constructed from explicit static features such
as consecutive loop depth and scalar reduction variables. This design is less
flexible than open-ended neural generation, but it is more predictable,
auditable, and aligned with the current objective: capture the most common and
safe pragma forms, including \texttt{parallel for}, \texttt{collapse(n)}, and
scalar \texttt{reduction} clauses, without hallucinating unsupported clauses or
unbound variables.

\subsection{Python-to-C++ Converter}

\subsection{Limitations}

The parallelizer is Linux-oriented because it depends on LLVM/Clang
development libraries and pybind bindings. It also depends on a remote
classifier endpoint unless local integration is added. The Python-to-C++
converter supports only simple syntax, so real Python programs with classes,
imports, comprehensions, lists, dictionaries, slices, exception handling, or
NumPy calls will not convert directly. The feature extractor is regex-based,
so it is fast and transparent but less semantically complete than full
dependence analysis.

\subsection{How to Use the Parallelizer}

After installing LLVM/Clang and building the project bindings, a user can
parallelize a C, C++, or supported Python file:

\begin{lstlisting}[language=Python]
from accelera.src.utils.parallelizer import parallelizer

parallelizer.parallelize("examples/loop_example.py")
# Writes examples/parallelized_loop_example.c
\end{lstlisting}

A simple Python input that the converter can handle is:

\begin{lstlisting}[language=Python]
total = 0
for i in range(0, 1000):
    total += i
print(total)
\end{lstlisting}

The converter emits C++; the parallelizer extracts the loop and can produce a
result similar to:

\begin{lstlisting}[language=C]
#include <iostream>

int main() {
    int total = 0;
#pragma omp parallel for reduction(+ : total)
    for (int i = 0; i < 1000; i++) {
        total += i;
    }
    (std::cout << total << std::endl);
    return 0;
}
\end{lstlisting}

\subsection{Execution Semantics}

Calling a \texttt{Pipeline} executes the underlying graph:

\begin{lstlisting}[language=Python]
predictions, executed_graph = pipe(X, y, select_strategy="all")
\end{lstlisting}

The C++ backend returns an executed graph plus result values. The Python layer
wraps the first returned item in \texttt{ExecutedGraph}; all remaining returned
items are predictions or metric outputs. The selection strategy can be
\texttt{all}, \texttt{max}, \texttt{min}, or a user-provided
\texttt{custom\_strategy}. Tests in the module show that these strategies are
used to select paths according to metric outputs.

\subsection{Preprocessing and Model Fitting}

Preprocess nodes store the transformation object or function together with
\texttt{execute\_fit}, a helper that determines whether a component should be
fit with \texttt{X} only or with both \texttt{X} and \texttt{y}. This lets the
pipeline handle unsupervised transformers such as scalers and supervised
transformers such as feature selectors. Model nodes similarly store the model
object and fitting helper, allowing sklearn-compatible estimators and custom
Accelera estimators to participate in the graph.

\subsection{Prediction Nodes}

\texttt{predict(name, test\_data, output\_func="predict", positive\_class=-1)}
records the data on which the trained model should be evaluated. The
\texttt{output\_func} parameter can request outputs such as \texttt{predict} or
\texttt{predict\_proba}. When probabilities are used, \texttt{positive\_class}
can select one probability column.

\subsection{Metric Nodes}

The pipeline maps metric names to functions from \texttt{sklearn.metrics}.
Then the metric-class helper inspects the metric function signature:

\begin{itemize}[leftmargin=*]
  \item A metric with true labels and predicted labels/scores becomes a
        \texttt{SupervisedMetric}.
  \item A metric with \texttt{X} and \texttt{labels} becomes an
        \texttt{UnSupervisedMetric}.
  \item Any incompatible signature is rejected.
\end{itemize}

\texttt{SupervisedMetric.execute} validates that \texttt{y\_pred} and
\texttt{y\_true} have the same number of samples, then calls the sklearn metric.
\texttt{UnSupervisedMetric.execute} validates predictions against the stored
input \texttt{X}. Both return a dictionary containing the metric name, result,
plot function, label names, and header names.

\subsection{Branching and Merging}

\texttt{branch()} accepts one or more branch node objects. Each branch can be a
single node or an iterable of nodes. The method validates that all branch
members are \texttt{Node} instances and rejects merge nodes inside branches
because merge-in-branch behavior is not implemented yet. The validated branch
objects, node types, and node names are passed to the C++ graph through
\texttt{split()}.

Merge nodes combine multiple branch outputs. The default strategy is
\texttt{hard\_voting}. The test suite covers hard-voting merges, merges after
preprocessing branches, probability prediction merges, single-model merges, and
reuse of executed graphs after merging.

\subsection{Executed Graphs}

\texttt{ExecutedGraph} wraps a graph that has already been fitted or selected.
Calling it with new \texttt{X} reuses the fitted pipeline. If \texttt{y\_true}
is provided, metrics are temporarily enabled for that call and disabled
afterward.

Executed graphs can now be persisted as a single pickle file. Calling
\texttt{save()} with no arguments creates \texttt{pipeline.pkl} in the current
working directory. The user may also pass an explicit file path such as
\texttt{"my\_pipeline.pkl"}. Loading is performed through
\texttt{ExecutedGraph.load()}, which reconstructs the native C++ graph and
restores the fitted Python objects stored in the graph nodes. The loaded graph
keeps the executed-state flag, so applying data to it performs inference
directly rather than fitting the models again.

\begin{lstlisting}[language=Python]
predictions, executed_graph = pipeline(X_train, y_train)

executed_graph.save()                  # writes pipeline.pkl
loaded_graph = ExecutedGraph.load()    # reads pipeline.pkl

test_predictions = loaded_graph(X_test)
\end{lstlisting}

The implementation uses a pybind pickle bridge for the C++ \texttt{Graph}
object. During saving, the graph is converted into a Python dictionary
containing node metadata, source-edge indices, selected-path flags, fitted
preprocessors, and fitted model state. During loading, this dictionary is used
to rebuild the graph topology and restore each node. This design stores the
pipeline in one file, but it requires the Python objects inside the pipeline to
be pickle-compatible; standard sklearn transformers and estimators satisfy
this requirement, while lambdas and some local custom functions may not.

\subsection{Reporting}

The reporting layer creates HTML reports rather than PDF reports. The base
class \texttt{ReportBase} defines the HTML shell and utility functions.
\texttt{GraphReport} reads serialized pipeline XML, builds a Graphviz diagram,
colors selected path nodes red and other nodes blue, lists branches, and then
delegates metric rendering to \texttt{GraphPipelineReport}.

The graph-pipeline report groups metric records by metric name and chooses a
display wrapper according to the result type:

\begin{itemize}[leftmargin=*]
  \item scalar values: \texttt{DisplaySingleNumber};
  \item one-dimensional arrays: \texttt{DisplayArraySingle};
  \item multi-dimensional arrays: \texttt{DisplayMultiArray} or
        \texttt{DisplayFigure};
  \item dictionaries: \texttt{DisplayDict};
  \item strings: \texttt{DisplayString};
  \item tuples: \texttt{DisplayTupleNotCurve} or \texttt{DisplayFigure}.
\end{itemize}

\texttt{ModelReport} reuses this metric rendering and can optionally plot

\section{Module-Level View}

The five report modules describe different layers of \project{}. The
\texttt{accelera\_pipe} module focuses on graph-based machine learning
workflow construction and execution. The code parallelizer focuses on source
loop analysis and OpenMP generation. The AutoML, deployment, and benchmark
platform sections are reserved for later module descriptions.

Across the implemented sections, a common architectural pattern appears:
Python exposes a convenient API and performs validation, while compiled or
external services provide lower-level parsing, execution, classification, or
infrastructure support.

\section{Conclusion}

The five-module structure illustrates the central engineering style of
\project{}: expose simple Python interfaces while using compiled
infrastructure, model services, and supporting platforms for
performance-sensitive or operational work. In the current report draft,
\texttt{accelera\_pipe} is documented as a graph-oriented ML workflow system
with branching, metric adaptation, path selection, executed graph reuse, and
HTML reporting. The code parallelizer is documented as a static-analysis and
OpenMP generation tool with a restricted Python converter, feature extraction,
classifier-based loop selection, and local heuristic fallbacks. The remaining
sections are intentionally left as space for future documentation.
